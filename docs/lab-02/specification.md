Lab 2 

1\) Sprint Goal



This sprint allows a requester to create an IT ticket with attachments, find their own tickets, and view or manage their attachments, all through a consistent Zen Green interface.



2\) Stakeholder Request Interpretation



The IT department wants an interface where requesters can submit their own support requests: describe the issue, choose a category and the affected system, set a priority, attach evidence, and then track their ticket. Since the real login doesn't exist yet, the user's identity is simulated with a temporary 'Development Requester' selector. The system must ensure that a Requester can never see someone else's tickets.



3\) Scope 



Included

&#x20;Ticket creation (Create Ticket) with validation

&#x20;Upload attachments when creating

&#x20;Automatic generation of the ticket number (Ticket Number)

"My Tickets" list: search, filters, sorting, pagination

&#x20;Ticket detail screen (read-only)

&#x20;Add an attachment to an existing ticket

&#x20;Soft removal of an attachment

&#x20;Protection: a Requester only sees their own tickets



Excluded

&#x20; Real authentication (login, password, sessions, tokens)

&#x20; IT Staff Dashboard (queue, ticket handling, changing IT Priority)

&#x20; Public Comments, Internal Notes, Actions Taken

&#x20; Any status changes after creation (the ticket stays 'New')

&#x20; Admin functions (user management, roles, reference data)



4\) Functional Requirements



&#x20;The system shall allow a requester to create a Ticket with Category, Related System, Requested Priority, Summary, Description, and optional Attachments.

&#x20;The backend shall generate a unique, human-readable Ticket Number on successful creation.

&#x20;The system shall let the Requester select their Development Requester identity before any ticket screen is accessible.

&#x20;The system shall let a Requester list only the Tickets they own, with search, category filter, priority filter, status filter, sorting, and pagination.

&#x20;The system shall let a Requester open a Ticket Detail screen for a Ticket they own, showing read-only ticket information.

&#x20;The system shall let a Requester add a permitted Attachment to their own Ticket, subject to the active-attachment limit.

&#x20;The system shall let a Requester download an active Attachment on their own Ticket.

&#x20;The system shall let a Requester soft-remove an Attachment they uploaded, with a required reason, keeping its metadata visible but making it non-downloadable.



5\) Business Rules



&#x20;Ticket defaults and system-generated values



&#x20;The official Ticket Number is generated by the backend and must be unique 

&#x20;A new Ticket begins with Current Status `New`.

&#x20;Ticket Date is set by the backend at creation time (server clock, stored UTC).

&#x20;IT Priority defaults to the same value as Requested Priority at creation (read-only for the Requester).

&#x20;Ticket Owner is null until assigned by IT Staff in a later lab.



&#x20;Development Requester context



&#x20;Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.

&#x20;Only active Development Requesters appear in the selector; inactive Requesters are excluded.

&#x20;Switching the Development Requester reloads all Requester-scoped data from scratch.

&#x20;If no active Development Requesters exist, the selector shows an empty state and blocks entry into ticket screens.

&#x20;If the active-Requesters API call fails, the selector shows a safe retry state instead of proceeding with a stale identity.



&#x20;Ownership



&#x20;A Ticket belongs to exactly one Requester (the one selected at creation time).

&#x20;All list, detail, and attachment endpoints filter or verify by requesterId server-side; the frontend's currently-displayed identity is     never trusted as an authorization decision.



Search, filtering, sorting, pagination



My Tickets search matches Ticket Number and Summary (case-insensitive, partial match).

Filters (Category, Requested Priority, IT Priority, Current Status) are combinable with search and with each other (AND logic).

Default sort is Created Date descending (newest first); Ticket Number, Summary, and Last Updated are also sortable, ascending or descending.

Default page size is 10; allowed page sizes are 10, 25, 50. Invalid page/pageSize values fall back to the defaults rather than erroring.



&#x20;Validation and duplicate-submission prevention



Ticket Summary is required, trimmed, 5–120 characters.

Ticket Description is required, trimmed, 10–2000 characters.

Category and Related System must reference active, existing records; Requested Priority must be one of the enumerated values (Low, Medium, High).

The Submit button is disabled while a create request is in flight, preventing duplicate submissions.

All Create Ticket validation is enforced both client-side and server-side; server validation is authoritative.



Failure behavior



If Ticket creation fails after validation passes, no partial Ticket is persisted and the form retains the Requester's entered values.

If the Ticket is created successfully but an attached file fails to upload, the Ticket is still saved; the failed attachment is reported with a clear per-file error, and the Requester may retry adding it from Ticket Detail afterward.



Attachment rules



&#x20;Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF only.

&#x20;Maximum attachment size is 5 MB per file.

&#x20;Maximum five active (non-removed) attachments per Ticket.

&#x20;Attachment removal is a soft removal: metadata remains visible but the file becomes non-downloadable.

&#x20;Removing an attachment requires confirmation and a required removal reason (min 3 characters).

&#x20;Only the Requester who owns the Ticket may add or remove attachments on it in Lab 2.

&#x20;Stored attachment filenames are randomized/generated server-side; the original filename is kept only as display metadata.



Inactive Requesters



An inactive Development Requester never appears in the selector and cannot create, view, or modify any Ticket.



Empty and no-results states



My Tickets shows a distinct "no tickets yet" empty state versus a "no results" state (filters matched zero of an existing set).



Ticket Detail access



Requesting a Ticket Detail by ID that does not belong to the selected Requester returns a not-found response; the API must not reveal whether the Ticket exists for another Requester.



Transition to Lab 3

The Development Requester selector is clearly labeled as temporary; Lab 3 replaces requester selection with real session-based authentication.

7) Data Changes



Models (Prisma), Int auto-incrementing primary keys, DateTime timestamps.



Category (existing from Lab 1): id, name (unique), createdAt



RelatedSystem (new): id, name (unique), createdAt



DevRequester (new): id, name, email (unique), isActive (Boolean, default true), createdAt



Ticket(new): id, ticketNumber (String, unique), requesterId (FK → DevRequester), 

categoryId (FK → Category), relatedSystemId (FK → RelatedSystem), summary (String), description (String), requestedPriority (enum: LOW/MEDIUM/HIGH), itPriority (enum, same values), currentStatus (enum, default NEW), createdAt, updatedAt



Attachment (new): id, ticketId (FK → Ticket, onDelete: Restrict), storedFileName (String), 

originalFileName (String), mimeType (String), sizeBytes (Int), uploadedAt (DateTime), isRemoved (Boolean, default false), removedAt (DateTime, nullable), removalReason (String, nullable)



Indexes `Ticket.requesterId`, `Ticket.ticketNumber` (unique), `Ticket.currentStatus`, 

`Attachment.ticketId`.



Soft removal represented by `Attachment.isRemoved` + `removedAt` + `removalReason`; the row is never deleted, and the download endpoint checks `isRemoved` before streaming the file.



8\) API Contract

See `api-spec.md` for full detail. Endpoints (all rooted at `/api/v1`, JSON, camelCase):



\- `GET /categories` — active Categories

\- `GET /related-systems` — active Related Systems

\- `GET /dev-requesters` — active Development Requesters

\- `POST /tickets` — create Ticket (+ optional attachments)

\- `GET /tickets` — paginated, filtered, sorted list of the selected Requester's own Tickets

\- `GET /tickets/:id` — one owned Ticket with its attachments

\- `POST /tickets/:id/attachments` — add an attachment

\- `GET /attachments/:id/download` — download an active attachment

\- `DELETE /attachments/:id` — soft-remove an attachment (with reason)



9\) Acceptance Criteria



\- AC-01: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.

\- AC-02: Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.

\- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned.

\- AC-04: Given a Summary shorter than 5 characters, when the Requester submits, then a field-level validation message appears and no API call is made.

\- AC-05: Given a 6 MB file, when the Requester attempts to attach it, then the file is rejected with a clear size-limit message before upload.

\- AC-06: Given a Ticket with 5 active attachments, when the Requester attempts to add a 6th, then the request is rejected client- and server-side.

\- AC-07: Given an uploaded attachment, when the Requester soft-removes it with a reason, then the attachment metadata remains visible but its download link is disabled.

\- AC-08: Given a soft-removed attachment, when any user attempts to download it directly by ID, then the server returns an error rather than streaming the file.

\- AC-09: Given zero tickets ever created for the selected Requester, when My Tickets loads, then the empty state (not the no-results state) is shown.

\- AC-10: Given search/filter criteria matching zero of several existing tickets, when applied, then the no-results state is shown with an option to clear filters.

\- AC-11: Given the backend is unreachable, when Create Ticket is submitted, then a safe failure state is shown and all entered field values are preserved.

\- AC-12: Given the Development Requester is switched from A to B, when My Tickets is viewed, then only B's tickets are shown and A's tickets are not visible even momentarily.

\- AC-13: Given the viewport is mobile-sized, when Create Ticket, My Tickets, or Ticket Detail are viewed, then no field label is clipped and no horizontal scrolling occurs.

\- AC-14: Given no active Development Requesters exist, when the selector loads, then an empty state is shown instead of a broken or blank dropdown.

11) Assumptions and Décisions



ID strategy: all new tables use Int auto-incrementing primary keys, consistent with the existing Category model from Lab 1 (not UUID).

Ticket Number format 

Auth deferral: the DevRequester model introduced here is temporary and will be replaced (not extended) by a real User/session model in Lab 3.

IT Priority visibility: shown as read-only, equal to Requested Priority in Lab 2, since no IT Staff workflow exists yet to change it.

- **URL identifier choice**: Ticket Detail and related endpoints use the internal `id` (not 
  `ticketNumber`) in the URL path for simplicity and consistency with Prisma's primary key. 
  `ticketNumber` remains the user-facing identifier shown in the UI and used for search, but 
  the API path relies on `id` since it's already indexed as the primary key and avoids a 
  second unique lookup.
